# 墨页本地评论设计提案

日期：2026-10-16。状态：设计已认可，候选版自测完成，待产品功能验收。目标版本：暂定 0.2.0。

实施和产品验收另行记录于 [评论实施记录](../implementation/feat-comments-v0.2.0.pending-acceptance.md)。设计认可不代表功能验收通过。

## 目标与范围

参考用户提供的飞书截图：选中文字后添加评论，正文高亮关联范围，右侧展示评论卡片。右栏与现有左侧文件/大纲栏独立展开、收起。

第一版定位为离线文稿批注：个人审阅、写作备忘、携带配套文件传递批注。作者使用本机昵称（默认“我”）和随机本地作者 ID；这不是身份认证。多人实时协作、账号、通知和 @ 提醒另作项目，不纳入第一版。

## 交互

### 布局

- 文稿工具栏新增“评论”按钮，显示当前文稿未解决线程数（不是回复数）。位置在源码切换附近，展开/收起操作始终可达。
- 右栏默认 300px，允许拖动到 300–440px。收起后正文回收空间，工具栏入口保留；不会关闭左栏。
- 展开状态及宽度写入 Settings；当前选中评论、筛选、滚动位置是每篇文稿的临时状态。打开另一篇文稿不会显示上一文稿的评论。
- 正文可用宽度至少保留约 520px：不足时右栏切换为覆盖右侧的抽屉，避免把正文挤成窄条；不擅自改变左栏偏好。抽屉需可键盘关闭并恢复焦点。
- 跟随素白、暖纸、深夜主题。右栏独立滚动；正文滚动不强制带动整个评论列表。点击关联内容时才做双向定位。

### 添加与阅读

1. 选择正文文字 → 右键“添加评论”、工具栏按钮或 Ctrl+Alt+M。
2. 在编辑器失焦前记录 selection bookmark 和文稿会话 ID；开启右栏，显示引用摘要和输入框。
3. Ctrl+Enter 发布，Enter 换行；输入法组合输入期间不触发发布。无选区则建立“整篇文稿”评论。
4. 一条线程包含引用、作者、时间、正文、回复、解决/重新打开、编辑及删除菜单。第一版只支持纯文本和换行。
5. 默认显示未解决线程，按正文顺序排列；全文评论置后，可切换查看已解决。解决后默认移出列表，保留历史；删除可短时撤销。
6. 点正文高亮 → 展开右栏并选中线程；点卡片引用 → 滚到原文。重叠范围显示一个小型线程选择器，不按点击次数随机轮换。
7. 收起侧栏不删除标记；保留较淡下划线，点击可重新展开。未解决标记用柔和暖色，选中后增强；已解决标记仅在查看对应线程时出现。
8. 收起/切换文稿时保留未发送输入到本地恢复草稿；只读文件、磁盘失败时明确显示未保存，不能把本地草稿状态显示成已保存到文稿。

### 源码模式的边界

第一版在即时编辑模式提供文字范围评论；源码模式可查看、回复、解决评论和添加全文评论，但暂不创建源码范围评论、不绘制精确字符高亮。切回即时编辑时重新解析并保守恢复定位，不能直接套用 ProseMirror 偏移。

第二阶段再提供 CodeMirror 范围批注适配器和 Markdown 源码/可见文本映射，覆盖 Markdown 标记、转义字符、前置属性、公式、表格与图片。两种编辑器的坐标体系不能共用一个 from/to。

## 评论定位

### 编辑过程

新增 ProseMirror 评论插件，沿用项目已有的 Plugin / DecorationSet 接入方式。评论高亮使用 Decorations，不加入正文 schema 的持久化 mark，不改变 Markdown 输出。

- 捕获选区时建立锚点；输入框内的输入不改变正文选区。
- 每次正文 transaction 通过 mapping 更新锚点范围，而不是每次全篇搜索引用。
- 范围边缘输入默认不扩大批注，范围内部修改跟随保留下来的内容。
- 保存创建时的 originalQuote 供用户查看，另维护 currentQuote 供重新定位；不把引用原文不断改写成新的话。
- 文本全部删除或被整体替换时标记 detached，保留原引用及所有回复；撤销正文删除可通过历史关联恢复锚点。
- 回复/解决不进入正文撤销栈；正文撤销与锚点映射需同步。不能只依赖 Decoration 被删除后的结果，否则撤销无法找回评论。

### 重开、模式切换和外部修改

持久化锚点同时记录：解析器/投影版本、可见文本投影位置、所在块路径和内容摘要、当前引用、前后文、原始引用、保存时文稿 hash。投影采用稳定的 UTF-16 偏移约定；行结束符归一为 LF，块边界使用明确分隔符，保留其他空白，不做破坏性 Unicode 归一化。

恢复顺序：

1. 正文 hash 和投影版本相同：校验持久化范围内的引用后恢复。
2. 正文变化：优先检查原块与邻接上下文；只有引用与上下文足够明确、候选唯一时自动恢复。
3. 多处相同文本、整体替换或候选缺失：标记 detached，显示“原文已变化，需要重新关联”。不把模糊匹配结果直接当作确认位置。
4. 用户选新范围，点“关联到所选文字”可手动恢复。内容相同但来源是复制粘贴时不自动复制评论。

第一版支持文本范围跨普通段落、加粗、链接和列表。图片/公式等非文本节点及跨复杂表格的范围先提示使用全文评论，避免不完整锚点；代码块内文本支持情况必须通过单独验收后开放。

## 本地存储

建议采用 sidecar：`文稿.md` + `文稿.md.moye-comments.json`。只在产生首条评论后创建配套文件；删除全部评论时保留空容器版本，避免旧同步副本重新引入已删评论。已有同名非墨页文件时停止写入并提示冲突。

配套文件是用户可携带的评论数据；应用 userData 只存偏好、恢复草稿和未完成写入记录。单独复制 Markdown 不会带走评论；分享时要一起携带配套文件。PDF/HTML 默认只导出正文，带批注导出放到后续阶段。

建议结构（示意，字段名实现时可调整）：

```ts
type CommentFile = {
  schemaVersion: 1
  documentId: string
  markdownHash: string
  revision: number
  projectionVersion: string
  threads: CommentThread[]
}
type CommentThread = {
  id: string
  status: 'open' | 'resolved'
  anchor: null | {
    state: 'attached' | 'detached'
    originalQuote: string
    currentQuote: string
    prefix: string
    suffix: string
    textFrom: number
    textTo: number
    blockPath: number[]
    blockFingerprint: string
  }
  messages: {
    id: string
    authorId: string
    authorName: string
    body: string
    createdAt: string
    updatedAt: string
  }[]
  createdAt: string
  updatedAt: string
  resolvedAt: string | null
}
```

null anchor 表示全文评论；attached/detached 与 open/resolved 是两个独立维度。日期使用 ISO UTC，界面用本机时区展示。内容长度、线程数量和总文件大小设置明确上限并验证，不能无界读取外部 JSON。未知更高 schemaVersion 只提示兼容问题，不能按空评论覆盖。

### 保存与恢复一致性

正文与评论不能宣称为跨文件原子事务。复用现有串行写队列，加一层文稿会话/修订标识和恢复记录：

1. 用户发布评论后，先把当前正文、评论、选区定位、未发输入和目标路径写入本机恢复草稿，成功前不显示“已保存”。
2. 正文未改变且有路径时，可单独原子写评论文件，但要复核正文 hash 和评论文件预期 hash。
3. 正文仍未保存时，评论标记“草稿”；按现有自动保存偏好调度正文与评论共同保存。关闭自动保存时不能因为发表评论偷偷落盘正文。
4. Ctrl+S：固定一份正文/评论快照 → 检查两个文件是否外部变化 → 写恢复记录 → 写正文 → 写与该正文 hash 对应的评论 → 清理已落盘的恢复记录。
5. 正文成功、评论失败时保留恢复记录，显示“正文已保存，评论待重试”。重开时用 hash 判断可恢复阶段，不覆盖已经被其他程序改过的正文或评论。
6. 保存期间继续输入，成功回调只确认此次快照；较新的修改继续保持 dirty，不能清空其恢复草稿。打开其他文稿后忽略旧会话的异步回调。
7. 未命名文稿可先评论，进入恢复草稿；第一次保存后才建立 sidecar。关闭/新建/打开的未保存检查同时检查正文、评论和未发送输入。
8. “另存为”复制评论和图片并产生新的 documentId；原文件不变。目标 sidecar 有既有数据时作为独立冲突处理；用户取消正文保存时不创建评论文件。
9. 应用外改名或移动只有 Markdown 时，不能可靠找到 sidecar。打开时提示可手动导入匹配的评论文件，并重新验证引用；只检查当前文稿相关文件，不扫描用户磁盘。
10. 评论文件也需监听外部变化。第一版不自动合并两个编辑者的批注修改；检测到变化时暂停写入，让用户载入磁盘版或保留副本，不静默覆盖。

目前在 OneDrive 工作区已观察到原子 rename 偶发 EPERM。上线前需要定位并增强保存：对明确的临时占用错误做有限退避重试，失败则保留恢复副本及清晰状态；不能用“先删除原文件再改名”来绕过。

前端只传已授权文稿标识/路径与预期版本；主进程推导 sidecar 路径并复用现有 sender/grant 校验。不得让渲染进程任意指定 JSON 写入路径，也不能跟随 sidecar 符号链接/重解析点写出文稿授权范围。回复以 React 文本渲染，第一版不接收原始 HTML。

## 交付顺序与验收

1. **保存基础**：定位 EPERM；实现 sidecar 格式、冲突检查、草稿与部分失败恢复。故障注入验证正文不会丢失。
2. **使用闭环**：右栏开关、全文/文本评论、回复、编辑、删除撤销、解决/重开、亮暗主题、窄窗和键盘操作。
3. **锚点闭环**：正文输入/删除/撤销、模式切换、重开、外部修改、重复文本与手动重新关联；最后再更新本机打包版。

必须通过的场景：

- 前方插入文字、范围内修改、删掉整个范围、撤销/重做，评论始终指向正确文字或明确显示失联。
- 重复句子、中文/emoji、CRLF、Markdown 格式归一化与前置属性，不误挂其他段落。
- 评论输入框内 Ctrl+S、Ctrl+Enter、中文输入法和全局快捷键不会意外改写正文；收起重开保留未发输入。
- 没改正文只新增/回复/解决评论，也必须持久化；切换文件和恢复时不能串文稿。
- 未命名、另存为、取消保存、只读、磁盘失败、评论 JSON 损坏、外部冲突、写一半崩溃都保留可恢复数据。
- 素白/暖纸/深夜，左右栏组合与 760px 最小窗口下均可操作；评论控件有 accessible name，焦点与滚动行为可预测。
- 现有单元测试、构建、Electron 端到端测试通过，尤其保存/冲突/图片/导出/草稿恢复无回归。

后续可扩展：源码范围批注、图片与公式批注、带评论导出、共享打包、多人离线评论合并。实时协作需要独立身份、同步与权限设计。
