# 项目设计、实施和验收记录

[开发者与 AI 入口](development/README.md) 说明项目设计、协作方式和源码运行；[用户首页](../README.md) 提供下载与使用说明。本页集中维护文档的目录、状态和记录要求。

## 目录与命名

- `development/`：开发者与 AI 的共同入口，说明项目设计与协作方式、代码结构、运行和发布。
- `design/`：功能范围、设计方案、取舍；设计认可不代表功能已交付。
- `implementation/`：实施记录，以可复现的验收场景、自测证据、产品反馈和交付结果为重点。
- 根目录 `CHANGELOG.md`：按最终版本索引产品已验收的变更。它是归档索引，不记录日常操作流水。

命名采用 `<type>-<topic>-v<target-version>[.<state>].md`，主题使用简短英文小写连字符。类型使用 `feat`、`fix`、`perf`、`refactor`、`docs`、`test`、`build`、`chore`。简单修复可直接建立实施记录，无需单独设计文档。

实施记录生命周期：

1. `.wip.md`：计划/开发/自测中；刚接到任务即可建档，明确实际进度。
2. `.pending-acceptance.md`：开发自测完成，已提供候选版本及验收步骤，等待产品确认。
3. 无状态后缀：产品明确验收通过，补齐结论和交付信息后正式归档。

开发完成不等于产品验收通过。设计获批、用户授权执行、自动化测试通过都不能替代产品验收。不通过或部分通过则保留未归档状态并继续修订，不能将未确认项写入已验收的发布日志。

## 版本绑定

- 每条记录必填目标版本；候选构建使用预发布号，如 `0.1.5-rc.1`。
- 同一交付版本可以包含多条记录；每次提交不必升级版本。
- 目标版本改变时同步改文件名、文档关联和索引。最终版本以实际交付为准。
- `package.json`、锁文件根版本和软件“帮助”显示保持一致；验收前不创建正式发布标签。
- 未知的最终版本、验收时间或提交号填写“待定/未提交”，不可假定完成。

## 实施记录最小内容

1. 类型、状态、目标版本、候选构建、最终交付版本、设计链接、相关提交。
2. 用户反馈、预期行为、复现条件、影响范围。
3. 事先写出的验收标准与操作步骤。
4. 原因、实现摘要、重要取舍及未覆盖项。
5. 实际自测结果、命令、测试环境及截图/数据等证据。不得把失败或未运行写为通过。
6. 产品验收栏：待确认项目、用户反馈原意、验收日期、通过/部分通过/返工结论。
7. 交付位置、版本和后续事项。

验收证据保存在 `implementation/evidence/<type>-<topic>-v<version>/`，只保留必要的合成文稿截图和检查摘要。包含用户隐私的文稿/截图不得默认复制到 Git；测试缓存与完整日志继续放在被忽略的 `test-results/`。

## 可选的判断与经验记录

为便于理解人与 AI 如何形成和修正判断，实施记录可以按需增加以下内容：

| 可选字段 | 适合记录的内容 |
| --- | --- |
| 初始判断 | 最初认为问题是什么、依据是什么、还有哪些不确定点。 |
| 用户纠正与方案变化 | 哪条用户反馈改变了判断或方案，以及为什么调整。 |
| 可复用经验 | 下次遇到同类问题时可采用的做法或需要注意的边界。 |

**以上三个字段均不是必填。** 可以选择部分，也可以全部省略；只在有实际内容时记录，不要求补写历史记录，不必保留空栏目，不为凑字段编造判断、纠正或经验。它们是现有实施记录的可选补充，不改变上面的最小内容与产品验收规则。
